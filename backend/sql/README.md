# База данни и миграции на FurniPro

## Кратък отговор за защитата

„Проектът използва PostgreSQL. Има **12 таблици на приложението и 1 служебна таблица**, общо **13 таблици**. Структурата се управлява чрез **13 номерирани SQL миграции** в `backend/sql`. Изпълнените миграции се записват в `schema_migrations`. Python моделите описват как приложението чете и записва данни; SQL миграциите създават и променят реалната PostgreSQL структура.“

## Къде е всяка таблица

| Миграция | Таблица / промяна | Предназначение |
| --- | --- | --- |

| `002_orders.sql` | `orders` | Поръчки на клиентите |
| `003_order_materials.sql` | `order_materials` | Материали и количества за поръчките |
| `004_materials_many_to_many.sql` | `materials`; разширява `order_materials` | Каталог на материалите и връзка много-към-много |
| `005_users_and_roles.sql` | `users`; разширява `customers` | Потребители, роли и връзка към клиент |
| `006_user_profiles.sql` | Разширява `users` | Име, телефон, град и активност; не създава таблица |
| `007_products.sql` | `fp_products` | Публични модели мебели |
| `008_configurations.sql` | `fp_configurations` | Запазени клиентски конфигурации |

Служебната таблица `schema_migrations` е описана в `bootstrap/schema_migrations.sql`. Този помощен файл **не е четиринадесета миграция**. Има 14 SQL файла за структурата, от които 13 са номерирани миграции.

## Какво е миграция

Миграцията е една последователна промяна в схемата: например създаване на таблица, добавяне на колона или външен ключ. Затова броят миграции не е задължително равен на броя таблици. `006` добавя колони към съществуваща таблица.

## Изпълнение и проверка

От `backend` в PowerShell:

```powershell
.\.venv\Scripts\python.exe manage.py migration-status
.\.venv\Scripts\python.exe manage.py migrate
```

`migration-status` само показва състоянието. `migrate` изпълнява чакащите файлове по номер. При стартиране FastAPI също проверява миграциите. `manage.py init` допълнително внася началните продукти и настройки, ако това още не е направено.

Използвай командата за мигриране вместо ръчно изпълнение на файловете, за да се попълва историята. При грешка транзакцията се отменя. Едновременно стартирани процеси се изчакват. Повторното изпълнение пропуска записаните миграции. Контролната сума открива промяна във вече приложен файл — следващите изменения се правят в нов файл, например `014_....sql`.

`001` и `002` описват възстановената начална структура, а `003`–`005` са съществуващите SQL файлове. При първото включване на механизма той изпълнява идемпотентните файлове върху съществуващата база и ги записва. Датите в `schema_migrations` показват кога механизмът е регистрирал миграцията, а не кога първоначално е създадена старата таблица.

В pgAdmin: избери базата → Schemas → public → Tables → Refresh. За точни числа и списък изпълни:

```sql
SELECT table_name
FROM information_schema.tables
WHERE table_schema = 'public' AND table_type = 'BASE TABLE'
ORDER BY table_name;

SELECT filename, applied_at
FROM schema_migrations
ORDER BY filename;
```

## Разграничения, които е полезно да знаеш

- `public_api.py` съдържа ORM модели за работа с таблиците, но не създава PostgreSQL таблици чрез `create_all`.
- `schema.py` и `Base.metadata.create_all` се използват единствено за изолираните SQLite API тестове. PostgreSQL миграциите се проверяват отделно върху временна PostgreSQL схема.
- `catalog.json` и `library.json` са начални **данни**, а не миграции на структурата.
- Изнасянето в SQL не нормализира JSON полетата: част от продуктовите характеристики и настройките все още са JSON текст в `payload`. Това е отделно бъдещо подобрение.
- `fp_order_links.legacy_order_id` е уникален идентификатор, но засега няма външен ключ към `orders`. Не го представяй като вече наложена връзка в базата.
